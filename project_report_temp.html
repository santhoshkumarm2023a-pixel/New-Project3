1. Executive Summary & Abstract

Modern academic campuses face critical security loopholes in conventional access control paradigms. Traditional Radio Frequency Identification (RFID) badges are susceptible to buddy punching, proxy attendance, and unauthorized entry via lost or stolen credentials. Conversely, standalone facial recognition terminals suffer from processing bottlenecks and fail to enforce physical continuity across multiple perimeter gates and academic blocks.

This project presents an end-to-end, multi-layered IoT security infrastructure that pairs physical RFID hardware with an edge artificial intelligence computer vision pipeline and smartphone mobile telemetry. Developed using Python 3.14, Arduino C++, OpenCV Deep Neural Networks (DNN), and SQLite with Write-Ahead Logging (WAL), the system enforces four simultaneous defense mechanisms:

  1. Physical Hardware Layer: An Arduino Uno / Freeduino 1.1 microcontroller communicating over a high-speed SPI bus with an NXP MFRC522 RFID transceiver, coupled with an active acoustic buzzer and dual status LEDs.
  2. Edge Biometric AI Layer: Simultaneous execution of OpenCV YuNet (ultra-fast face detection) and OpenCV SFace (128-dimensional deep feature embedding extractor), verifying the swiper's identity against enrolled portraits at a strict cosine similarity threshold (≥ 0.44).
  3. Dual-Factor Mobile Geofencing: Real-time integration with a background Telegram Mobile Guard daemon (@vit_security_007_bot), computing geodesic surface distances between the reader terminal and the student's live 4G/5G smartphone satellite coordinates. Swipes occurring outside the configurable geofence (50m–1200m) trigger immediate access lockout and instant forensic Telegram push alerts.
  4. Physical Zone Containment & Continuity Engine: A finite state machine enforcing logical physical trajectories (OUTSIDE ↔ CAMPUS_TRANSIT ↔ INSIDE_BUILDING), eliminating ghost presence and impossible concurrent entries.
Key Achievement:
The system achieves sub-second end-to-end verification latency (~120ms total pipeline execution), guarantees 0% proxy attendance through terminal CCTV face matching, and serves an enterprise real-time web surveillance portal deployed via Streamlit.

3. RF Tuning & Firmware State-Machine Engine

3.1 The ISO 14443-A Card Sleep Problem & Solution

A universal flaw in basic MFRC522 tutorials is that standard example sketches call PICC_HaltA() followed by PCD_StopCrypto1() after reading a card's UID. Under ISO 14443-A specifications, passive Mifare cards transition from the ACTIVE state into the HALT state when halted. In the HALT state, the card's internal microcontroller ignores standard REQA (0x26) requests.

Furthermore, standard PICC_IsNewCardPresent() library calls send REQA. Consequently, once a card is swiped once, it fails to be detected on subsequent swipes until its internal charge pump capacitor completely discharges.

3.2 The Dual-Mode Fast Polling Engine (getCard())

To achieve 100% reliable, instantaneous card detection regardless of whether a card is fresh, recently swiped, or held in the RF field, our firmware implements an intelligent dual-mode polling function: 

// Dual-mode card polling: handles fresh IDLE cards (REQA) AND sleeping/halted cards (WUPA)
boolean getCard() {
  // 1. Try standard instant check (REQA) - < 1ms execution time
  if (rfid.PICC_IsNewCardPresent()) {
    return rfid.PICC_ReadCardSerial();
  }

  // 2. If that fails, wake up sleeping or fast re-swiped card (WUPA - 0x52)
  byte bufferATQA[2];
  byte bufferSize = sizeof(bufferATQA);
  if (rfid.PICC_WakeupA(bufferATQA, &bufferSize) == MFRC522::STATUS_OK) {
    return rfid.PICC_ReadCardSerial();
  }

  return false;
}

3.3 Receiver Saturation Prevention via Calibrated Gain

Low-cost MFRC522 clone modules (identifying as chip signature 0xB2) suffer from RF frontend saturation when configured with RxGain_max (48 dB). At 48 dB, reflected carrier magnetic waves overwhelm the analog comparator pins, effectively blinding the receiver when a card is held close to the PCB.

Our firmware specifically configures antenna gain to RxGain_43dB (43 dB) via register RFCfgReg. This provides double the read distance (~4.5 cm) compared to default factory gain (33 dB), while completely avoiding frontend receiver saturation.

3.4 Actuator Feedback Frequency Tuning

Active buzzers possess an internal mechanical resonance peak at 2000 Hz – 2400 Hz. Previous low-frequency signals (e.g. 800 Hz) resulted in inaudible diaphragm chatter. The actuator engine was reprogrammed with distinct, human-audible frequency signatures:

  • Access Granted ('G'): Melodic rising frequency — 1800 Hz (80ms) followed by 2200 Hz (100ms) alongside Green LED illumination.
  • Access Denied ('D'): Three rapid, urgent warning alarm pulses — 2200 Hz (80ms) spaced by 100ms pauses alongside Red LED illumination.

4.2 Multi-Process Concurrency Design

To ensure instantaneous hardware responsiveness while maintaining an interactive dashboard, the system separates responsibilities across independent, asynchronous processes:

  • Serial Bridge Daemon (serial_bridge.py): Runs continuously in the background. It maintains an exclusive serial connection with the Arduino on COM5, streams frames from the biometric CCTV webcam, runs the YuNet and SFace neural networks, evaluates security rules, updates the SQLite database, and communicates with Telegram.
  • Surveillance Dashboard (app.py): Serves the operator web interface over HTTP (http://localhost:8501). It renders real-time access tables, audit violations, forensic evidence popovers, CCTV monitor feeds, and system configuration controls.
  • Database Synchronization via WAL Mode: Both processes access campus_security.db simultaneously. By enabling SQLite's Write-Ahead Logging (WAL) mode, reading processes in Streamlit never block the high-priority write transactions of the serial bridge, preventing database locking and interface stutter.

5. Computer Vision & Biometric AI Pipeline

Traditional access control systems verify only the possession of an RFID card. This project introduces a non-intrusive 1-to-1 biometric facial identity verification pipeline executing at the edge in real time.

5.1 YuNet Deep Learning Face Detector

The system employs YuNet (stored as yunet.onnx), a cutting-edge, lightweight convolutional neural network optimized for fast face detection on edge CPUs. YuNet operates on arbitrary input resolutions and produces high-precision bounding boxes alongside five facial landmark points (eyes, nose, mouth corners) in under 15ms.

  • Score Threshold: 0.50 (eliminates false positives from ambient classroom/hallway objects).
  • NMS Threshold: 0.30 (merges redundant overlapping detections).
  • Top-K Candidates: 5,000 max proposals.

5.2 SFace 128-D Deep Facial Feature Recognizer

Once a face is detected, the region of interest is aligned and cropped using the 5 landmark points to normalize rotation and tilt. The cropped face is then processed by SFace (stored as sface.onnx), an efficient deep convolutional neural network designed for facial feature representation.

  • Feature Representation: Produces a normalized 128-dimensional floating-point vector uniquely identifying facial geometry.
  • Feature Pre-Caching: Enrolled student photos (stored as registered_faces/{UID}.jpg) are processed once at system startup. Their 128-D vectors are cached in memory in a hash map, reducing live matching time to less than 1 millisecond.
  • Similarity Metric: Cosine similarity between live vector and enrolled vector (threshold ≥ 0.44). Scores ≥ 0.44 confirm authentic cardholder presence; scores < 0.44 flag an unauthorized impostor swiping a stolen card.

6. Dual-Factor Mobile Geofencing & Stolen Card Guard

One of the primary research novelties in this architecture is the Dual-Factor Mobile Geolocation Engine. Even if an attacker obtains a student's RFID card and attempts an unauthorized swipe, the system verifies whether the legitimate cardholder's mobile smartphone is physically co-located at the reader terminal.

6.1 Real-World GPS Geodesic Surface Distance

All campus terminal stations are mapped with real-world WGS-84 geographic coordinates. When a card is swiped at a terminal, the system queries the live coordinates of the student's mobile device (streamed via Telegram 4G/5G mobile GPS) and calculates the surface geodesic distance using WGS-84 ellipsoid modeling via Geopy.

6.2 Geofence Evaluation & Intrusion Detection

The system administrator configures an acceptable geofence threshold $R_{\text{geo}}$ (default 50 meters, adjustable up to 1,200 meters via the dashboard sidebar).

  • If $\text{Distance} \le R_{\text{geo}}$: The cardholder's mobile device is physically adjacent to the reader station. Geolocation is verified.
  • If $\text{Distance} > R_{\text{geo}}$: The card was swiped at a campus reader, but the student's smartphone is hundreds of meters or kilometers away (e.g. in a hostel room or off-campus cafeteria). Access is denied immediately as a GEOLOCATION BREACH (STOLEN CARD).

6.3 Telegram Mobile Guard Integration (@vit_security_007_bot)

The system operates an active Telegram bot daemon (telegram_guard.py) enabling two-way mobile interaction:

  • Live Telemetry Ingestion: Students send their live location pin via Telegram. The daemon extracts the satellite GPS payload and updates the student's coordinates in the SQLite database in real time.
  • Critical Intrusion Push Alerts: When any violation occurs (proxy attempt, face mismatch, or stolen card geofence breach), the daemon dispatches an instantaneous alert directly to the cardholder's phone with terminal name, violation details, and timestamp.
  • Legitimate Entry Notifications: On successful access, the student receives a confirmation message showing entry station and distance.

8. Database Architecture & Table Chronology

8.1 Relational Database Schema (SQLite WAL)

The database file campus_security.db maintains structured relational tables storing user directory profiles, audit logs, and hardware configurations:

  • users: Stores uid (Primary Key), student name, reg_no, role, occupancy, current_building, photo path, telegram_chat_id, and live mobile coordinates (phone_lat, phone_lon, phone_last_ping).
  • access_logs: Auto-incrementing id (Primary Key), time (HH:MM:SS), timestamp (ISO-8601), user_name, card_uid, reg_no, role, status, door, place, and forensic snapshot image path.
  • security_violations: Auto-incrementing id (Primary Key), time, timestamp, user_name, card_uid, reg_no, violation_type, details, severity, door, and evidence snapshot.
  • system_config: Key-value store persisting runtime policy toggles (geolocation guard on/off, geofence radius, active reader terminal door).

8.2 Chronological Inversion Fix (S.No 1 Guarantee)

Technical Problem Resolved:
Earlier versions of the application sorted access feed tables using raw string timestamps (e.g. HH:MM:SS), causing morning swipes to sink beneath evening entries. Furthermore, heuristic fallback keys in database persistence created ordering inversions.

The database architecture was re-engineered with two structural guarantees:

  1. Every log entry is assigned an explicit, auto-incrementing integer primary key (id INTEGER PRIMARY KEY AUTOINCREMENT) and an ISO-8601 timestamp (timestamp TEXT).
  2. Queries retrieve access feeds and security audits strictly ordered by auto-increment ID descending: 
    SELECT * FROM access_logs ORDER BY id DESC LIMIT 100;
  3. In Streamlit, the table rendering function sorts entries strictly by key=lambda x: x.get("id", 0), reverse=True. This guarantees that the most recent swipe is always S.No 1 at the top of the table.
  4. Streamlit fragment refresh intervals were updated from 2 seconds to 1 second (run_every="1s"), delivering sub-second live table repainting as soon as a card is swiped.

10. Viva Voce & Technical Oral Examination Q&A

Q1: What is the primary novelty of this access control system over existing RFID solutions?

Answer: Existing commercial systems suffer from proxy attendance (buddy punching) and stolen card reuse. Our architecture provides a three-factor verification triangle: (1) physical possession of the RFID credential, (2) edge AI 1-to-1 biometric facial recognition via YuNet and SFace, and (3) mobile device co-location via geodesic smartphone GPS geofencing with Telegram integration. All swipes are validated against a physical zone containment finite state machine.

Q2: Why did you choose YuNet and SFace over traditional Haar Cascades or dlib?

Answer: Haar Cascades are computationally brittle, highly sensitive to lighting changes and head tilt, and lack feature vector embeddings. Dlib's ResNet model is computationally heavy and introduces unacceptable latency (~400ms) on edge hardware. OpenCV's YuNet operates in <15ms with high occlusion tolerance, and SFace extracts a lightweight 128-dimensional embedding in <50ms, allowing our entire biometric pipeline to execute in under 70ms on standard CPUs.

Q3: How does the MFRC522 communication protocol prevent card read lockups?

Answer: In standard ISO 14443-A operations, calling PICC_HaltA() places a card into the HALT state where it ignores standard REQA requests. We designed a dual-mode polling engine (getCard()) that issues REQA first, and if unacknowledged, automatically transmits WUPA (Wake-Up Type A, 0x52) to wake sleeping or rapidly re-swiped cards. We also tuned antenna gain to RxGain_43dB to prevent analog receiver saturation on clone ICs.

Q4: How do the Serial Bridge and Streamlit Dashboard communicate without database locking?

Answer: Both processes communicate through a shared SQLite database (campus_security.db) configured with Write-Ahead Logging (WAL) mode. In WAL mode, writes are appended to a separate .db-wal file rather than overwriting database pages directly. This enables concurrent multi-process access: Streamlit's read queries never block the Serial Bridge's high-priority hardware write transactions.

Q5: How does the Geofencing algorithm compute distances between phone and terminal?

Answer: The system stores precise WGS-84 geographic coordinates for every campus gate and academic block. When a swipe occurs, the student's mobile GPS latitude and longitude (streamed via Telegram Bot) are compared against the reader's GPS using geodesic surface calculation (solving inverse geodesic problems on the WGS-84 ellipsoid). If the geodesic distance exceeds the configured threshold (e.g. 50 meters), the card is flagged as stolen.

Q6: What is the significance of the Zone Containment Engine?

Answer: It prevents "ghost presence" and impossible physical movements. For example, a student cannot enter an academic building if their occupancy state is OUTSIDE (meaning they bypassed the perimeter turnstile), nor can a student be simultaneously logged into two different academic towers. The FSM enforces physical continuity across all access points.
